# Gap analysis: ветка mobile-check относительно целевой архитектуры RPG-LIFE

- Дата проверки: 2026-11-10
- Проверяемая ветка: `mobile-check` (head `3bcd9d6f9e72b70959ed904c7160a18d658bc704`)
- Целевая спецификация: [ARCHITECTURE_DECISION.md](./ARCHITECTURE_DECISION.md)
- Статус: аудит исходного кода и документации; код не запускался и runtime-поведение не подтверждено

## 1. Краткий вывод

`mobile-check` содержит полезный React/Hono/MySQL прототип и переносит заметную часть игрового ядра. Но это не готовый кандидат для production merge. Есть блокирующие расхождения в авторизации, миграциях БД, локальной изоляции аккаунтов и конкурентной синхронизации.

Главное: не продолжать разработку поверх текущей auth/save-реализации до исправления этих проблем. Сначала подтвердить Identity Provider, затем выстроить серверную модель аккаунта и атомарное сохранение.

| Область | Что обнаружено в mobile-check | Статус |

## 3. Блокирующие технические проблемы

### P0 — Авторизация не соответствует требованию

Файл: `app/api/anonymous-auth.ts`.

Сейчас пользователь автоматически получает анонимный профиль через `/api/auth/bootstrap`. Восстановление выполняется через многоразовый recovery code. Это не Kimi OAuth и не полноценная внешняя идентификация.

Кроме того, rate limiter хранит счётчики в локальном `Map` процесса. При нескольких инстансах лимит не общий, а после рестарта сбрасывается.

Решение:
- не переносить эту auth-модель в production;
- подтвердить официальный способ Kimi OAuth для сторонних приложений;
- если Moonshot не предоставляет такой сценарий, выбрать отдельный Identity Provider;
- rate limiting перенести в общий store/DB/Redis и ограничить не только bootstrap, но и recovery endpoints.

### P0 — Синхронизация не обеспечивает compare-and-swap

Файлы: `app/api/save-router.ts`, `app/api/queries/saves.ts`.

Текущая логика разрешает запись, если выполняется хотя бы одно условие:
- revision совпадает;
- клиентский `state.updatedAt >= current.payload.updatedAt`.

Это означает, что несовпадающая revision не всегда приводит к конфликту: клиент с более поздним timestamp может перезаписать текущий сейв. Дополнительно чтение текущей версии и последующий UPDATE выполняются отдельными запросами, без атомарного условия `WHERE revision = expectedRevision` и без транзакции.

Решение:
- атомарный UPDATE с условием по ожидаемой revision;
- проверять affected rows;
- при нуле обновлённых строк возвращать conflict и актуальную серверную revision;
- создание первой записи делать через уникальный ключ и обработку duplicate key;
- timestamp использовать для диагностики/сортировки, но не как замену CAS.

### P0 — Локальные данные не разделены по аккаунтам

Файл: `app/src/store/gameStore.ts`.

Zustand persist использует постоянный ключ `life-rpg-local-v1`, не включающий user ID. После смены аккаунта в одном браузере локальный профиль остаётся общим. Это может привести к отображению или отправке состояния предыдущего аккаунта.

Решение:
- namespace IndexedDB/local persistence по стабильному account ID;
- гостевой профиль должен иметь отдельный идентификатор;
- logout должен очищать активное состояние в памяти, но не удалять чужие локальные сейвы;
- переключение аккаунта должно сначала загрузить правильный namespace и только затем разрешать sync;
- добавить тесты account A → logout → account B → reload → account A.

### P0 — Миграции MySQL не готовы к воспроизводимому deploy

В `app/db/migrations/` присутствуют `.gitkeep` и metadata, но SQL-файл миграции, указанный в journal (`0000_clever_blonde_phantom.sql`), в дереве не найден. Deployment guide также предупреждает об отсутствующем migration file для anonymous recovery.

Следствие: чистое развёртывание по `drizzle-kit migrate` нельзя считать воспроизводимым по текущему содержимому ветки.

Решение:
- сгенерировать миграции из schema;
- проверить их на пустой MySQL database;
- проверить повторный запуск/отсутствие повторного применения;
- проверить upgrade path с тестовой существующей БД;
- не использовать `drizzle-kit push` на production как замену миграциям.

## 4. Функциональная полнота продукта

Источник: `app/FUNCTIONAL_MIGRATION.md`, страницы React и store.

### Игровое ядро — хорошая основа, но не паритет

Есть:
- CRUD квестов, привычки, поиск/сортировка/фильтры, архив;
- начисление и отмена XP;
- уровни, streak, activity dates;
- направления и редактируемое дерево навыков;
- цели с горизонтом и прогрессом от связанных квестов;
- локальное хранение IndexedDB, JSON import/export, Markdown export;
- базовая рефлексия и lore.

Не перенесено или неполно:
- отдельная лента истории действий;
- глобальная история undo и менеджер резервных копий;
- карточка узла с отдельной практикой/мастерством;
- ключевые навыки;
- полноценные панорамирование/навигация дерева;
- экипировка титулов и отдельный level-up overlay;
- rest day и вечерний ритуал;
- полноценный lore journal и недельный обзор;
- полный набор тем, справка, примеры деревьев и microtips.

### AI — функции есть, но это ещё не долгосрочный наставник

В `app/api/ai-router.ts` поддерживаются режимы `diagnose`, `tree`, `day`, `direction`, `mentor`. Ответ проходит Zod-схему, квестам рассчитывается XP, а UI оставляет результаты черновиками до подтверждения.

Ограничения:
- каждый вызов stateless: история диалога не сохраняется;
- в контекст передаются вопрос, направление, стадия, существующие навыки, время и энергия;
- не передаются фактическая история завершённых квестов, прогресс целей, динамика XP и предыдущие решения наставника;
- нет долговременной памяти наставника и механизма регулярного пересмотра маршрута;
- генерация дерева ограничена коротким плоским списком узлов, а не полноценным богатым деревом.

Следующий продуктовый шаг после исправления основы: отдельная модель MentorSession/MentorMessage, сбор разрешённого контекста прогресса и явное подтверждение любых изменений состояния.

### Цели — только базовый уровень

Сейчас цель имеет название, горизонт, числовой target/current, единицу измерения и необязательное направление. Это рабочая основа, но нет дерева этапов/milestones, зависимостей и автоматического отчёта по прогрессу к большой цели.

## 5. Тестирование и deploy

Обнаружены unit-тесты прогрессии и маппинга ошибок AI. Полноценные браузерные E2E тесты в репозитории не обнаружены. Поэтому нельзя считать подтверждёнными сценарии на iPhone, auth switching, offline/online sync, конфликт двух устройств и полный AI workflow.

Deployment guide прямо указывает, что GitHub Pages не запускает Hono/MySQL и для этой версии нужен Node.js hosting + MySQL. Фактический production backend deploy по одной только ветке не подтверждён.

## 7. Решение по mobile-check

Ветка содержит полезные компоненты, но не должна сливаться целиком. Её следует использовать как исходник для выборочного переноса после исправления P0. PR #1 закрыт без merge; сама ветка пока сохранена в репозитории.

Аудит основан на чтении исходников и документации GitHub. Код и тесты в этой проверке не запускались; все перечисленные runtime-поведения должны быть подтверждены тестами до production.
