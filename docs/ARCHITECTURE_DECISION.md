# Architecture Decision Record: целевая архитектура RPG-LIFE

- Статус: предложено для следующего поколения; текущий production не меняется
- Дата: 2026-11-10
- Основа решения: текущий `main`, закрытый PR #1 (`mobile-check`), слитый PR #3 и ранее зафиксированные требования владельца проекта

## 1. Контекст

В репозитории существуют две несовместимые линии реализации:

1. Production `main`: статическое приложение на HTML/CSS/JavaScript, Supabase Auth/Database и Supabase Edge Function для AI Proxy. Оно уже прошло ручной smoke test и CI/deploy.
2. Закрытый PR #1 / ветка `mobile-check`: отдельное приложение React + TypeScript + Vite, Hono + tRPC, Drizzle + MySQL, анонимная cookie-сессия и Groq. Это не просто workflow-проверка, а альтернативная реализация продукта.

Сливать PR #1 целиком нельзя: в нём другая модель авторизации, другой backend, другая база и другая модель развёртывания. Одновременно заменять работающий production без подтверждённого функционального паритета рискованно.

## 2. Целевое решение

Для следующего поколения RPG-LIFE принять следующую целевую архитектуру:

| Слой | Решение |
|---|---|
| Frontend | React + TypeScript + Vite, mobile-first PWA |
| API / backend | Hono + tRPC, серверная валидация Zod |
| Database | MySQL через Drizzle ORM и версионируемые миграции |
| Authentication | Kimi OAuth как требование продукта; интеграцию подтвердить отдельным техническим spike до реализации |
| AI | Серверный AI Gateway / AI SDK; Groq остаётся поставщиком inference-модели |
| AI credentials | Только серверные secrets; никакого API key в браузере или `VITE_*` |
| Hosting | Node.js hosting для полного стека (целевой вариант — Railway); frontend и API по возможности на одном origin |
| Local-first | IndexedDB для офлайн-состояния; облачная синхронизация по account ID и revision |
| Data safety | Версионированный save, compare-and-swap, backup/restore, миграции и ID-aware import |

Kimi OAuth относится только к идентификации пользователя. Kimi/Nano не используется как AI-модель. Генерация и ответы AI продолжают маршрутизироваться через Groq.

### Обязательная проверка Kimi OAuth

До проектирования production auth необходимо подтвердить, что выбранный Kimi OAuth flow действительно подходит для стороннего приложения: наличие официального authorization endpoint, token exchange, user identity endpoint, redirect URI rules, scopes, PKCE/state и допустимые условия использования.

Не заменять это незаметно анонимной cookie-сессией. Если Kimi OAuth недоступен или не подходит, подготовить отдельное сравнение провайдеров и получить решение владельца до смены требования.

## 3. Граница миграции

- Текущий `main` остаётся стабильной production-версией до прохождения критериев функционального паритета.
- GitHub Pages подходит для текущей статической версии, но не запускает Hono и MySQL. Полноценная целевая версия должна развёртываться на Node.js-хостинге.
- `mobile-check` рассматривается как источник кода и прототип, а не как готовая ветка для merge.
- Переносить функции поэтапно: сначала contracts и доменная модель, затем store и persistence, затем API/auth, затем AI, UI и миграция данных.
- Не удалять legacy-реализацию до подтверждённого переноса пользовательских данных и сценариев.
- Не выполнять destructive database migrations без backup, dry-run и отдельного согласования.

## 4. Функциональный контракт

Новая версия должна сохранить или явно улучшить все основные возможности:

1. Профиль героя, уровни, XP и история начислений.
2. Квесты: ручные и AI-сгенерированные, типы/сложность/критерии завершения, редактирование, отмена и защита от повторного начисления.
3. Привычки, streak и корректное поведение при смене локальной даты.
4. Направления развития и интерактивное дерево навыков.
5. Долгосрочные цели, этапы и привязка к навыкам/квестам.
6. AI-наставник с контекстом пользователя, истории и текущего прогресса.
7. Экспорт, импорт, резервные копии и восстановление.
8. Гостевой/локальный режим и облачная синхронизация аккаунта.
9. Работа на iPhone, адаптивный интерфейс и offline-first базовые сценарии.

AI может предлагать изменения, но не должен незаметно изменять прогресс, выдавать XP или переписывать маршрут без подтверждения пользователя.

## 5. Обязательные архитектурные инварианты

- Все записи облака строго изолированы по account ID.
- Локальные данные разных аккаунтов разделены; переключение аккаунта не может показать или отправить данные предыдущего аккаунта.
- Конфликт сохранений решается revision/CAS на сервере, а не только сравнением клиентских timestamp.
- Повторный запрос/повторное нажатие не начисляет XP повторно (idempotency).
- Клиент не имеет доступа к AI provider secrets и privileged database credentials.
- AI output валидируется схемой и считается черновиком до подтверждения.
- Миграции БД воспроизводимы на пустой тестовой БД и проверяются до production.
- Сбои сети или AI не блокируют ручные квесты и локальный прогресс.

## 6. План перехода

### ADR-1 — подтверждение авторизации
Провести Kimi OAuth spike: документировать официальный flow, необходимые secrets, callback, PKCE/state, user ID mapping, logout и refresh/revocation. Результат — работающий proof-of-concept в непроизводственной среде либо обоснованное заключение о невозможности.

### ADR-2 — backend и база
Поднять тестовый Hono/tRPC API и MySQL на отдельном окружении; описать schema/migrations, auth middleware, account isolation, rate limits и save CAS. Проверить миграцию на пустой БД.

### ADR-3 — функциональный паритет
Составить таблицу legacy → target для каждого экрана и действия. Каждый пункт должен иметь статус: реализован, тестируется, отсутствует или сознательно изменён.

### ADR-4 — автоматизированная проверка
Добавить unit/integration/E2E тесты: новый профиль, quest lifecycle, XP idempotency, skill tree, AI draft approval, logout/login, два аккаунта, offline/online sync, export/import и восстановление.

### ADR-5 — staged rollout
Развернуть target отдельно от production. Провести миграцию тестовых данных, ручной smoke test на iPhone, проверку backup/restore и только затем принимать отдельное решение о переключении production.

## 7. Критерии готовности к переключению production

- Kimi OAuth подтверждён и работает в тестовой среде либо владелец отдельно утвердил альтернативу.
- Все пункты функционального контракта имеют рабочую реализацию или явно утверждённое изменение.
- CI включает typecheck, unit/integration tests, production build и браузерные E2E.
- Проверены изоляция двух аккаунтов, восстановление на новом устройстве и конкурентное обновление сейва.
- Подтверждены backup/restore и миграция данных без потери прогресса.
- AI недоступность не ломает базовое приложение; секреты не попадают в клиент.
- Ручной smoke test на iPhone пройден.
- Есть проверенный rollback-план.

## 8. Что не делать сейчас

- Не сливать PR #1.
- Не переписывать текущий production `main` напрямую.
- Не запускать `drizzle-kit push` на production вместо проверенных миграций.
- Не переносить авторизацию на анонимные cookie-сессии вопреки требованию Kimi OAuth.
- Не менять Groq на Kimi/Nano как модель.
- Не добавлять социальные функции и монетизацию до устойчивого core loop.

## 9. Следующие конкретные задачи

1. Проверить официальный Kimi OAuth flow и сделать минимальный proof-of-concept.
2. Сверить текущую React/Hono/MySQL реализацию с этим ADR и отметить расхождения.
3. Подготовить функциональную матрицу legacy → target, включая AI mentor, AI quest generation и skill tree.
4. Подготовить отдельное тестовое окружение backend + MySQL и воспроизводимые миграции.
5. Добавить E2E-критерии до переноса production.
